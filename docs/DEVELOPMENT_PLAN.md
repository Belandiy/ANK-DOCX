# Первый этап разработки

Статус: первая техническая реализация создана 29 октября 2026 года в academic/. Актуальные возможности, ограничения и команда запуска приведены в academic/README.md. Ниже сохранены критерии и последовательность этапа; полное выполнение последующих этапов, включая реальный профиль СТО и анализ страниц, не заявляется.

Служебная инфраструктура перенесена с собственных Python/PS1 на C#; Quarto, R и Lua сохраняют свои задачи. Состояние реализации и свидетельства — в [приёмке миграции](research/SERVICE_LAYER_MIGRATION.md). Прямые преобразования пакета в R-hook пока сохранены; новый общий сборщик не вводился.

## Решение

Обзор технологий достаточен для начала разработки. Основа авторского проекта — стандартный Quarto Book, исходники QMD и университетский формат как расширение Quarto. Базовый вычислительный путь первой версии — knitr + R + flextable. Для работ, не исследующих конкретный язык программирования, расчёты выполняются на R. Специальный исследуемый программный проект сохраняет свой язык и собственный способ исполнения.

Основной путь научной графики — ggplot2 → svglite → SVG в DOCX; резервный растровый экспорт — ragg, 600 dpi. TikZ, PGFPlots и quarto_tikz исключены из рабочего стека. Их исследование завершено; интеграция и установка TeX для графиков в план разработки не входят. LaTeX-разметка математических выражений в QMD и их преобразование в OMML сохраняются.

Критерий выбора — работа агента над каждой работой, наш код, интеграция готовых библиотек, зависимости и дальнейшее сопровождение. Количество строк экспериментального стенда само по себе не является стоимостью продукта.

Подтверждённый Quarto-вариант с Word-адаптером сохраняется как контроль. Его полный сравнительный стресс-тест заново не проводится. Новый Book и новые объекты проверяются точечно, потому что прежний C использовал project.type: default с includes.

## Первый результат

Небольшой стандартный Book-проект с подключённым настоящим format extension собирает один DOCX одной командой Quarto. Пример демонстрирует законченный путь от авторских файлов до Word, а не только установку расширения.

Команда созданного формата: `quarto render --to academic-docx`. В подготовленном окружении текущего репозитория также доступен build-academic.cmd.

В примере: метаданные работы, титульный лист, краткая аннотация, оглавление, две содержательные главы, вычисляемая таблица, один график, нумерованная формула, ссылки и небольшой набор источников. Используется имеющийся Word-шаблон как техническая основа; полное соответствие конкретному СТО до отдельной сверки не заявляется.

## Порядок реализации

1. Создать формат штатной командой Quarto. Подключить reference.docx, общие настройки и стандартный список book.chapters. Метаданные и исходники не переводить в самодельный формат. Выяснить, какие части существующих фильтров нужны для Book, а какие обслуживали только сравнение A/B/C.
2. На коротком разделе проверить прямой путь knitr + R + flextable. R считает f(x)=a*x^2+b и g(x)=2*x при x=2,3,4 и формирует данные для текста, таблицы и графика. При a=3, b=1 сумма равна 108; при a=5 — 166. Расчёт задан один раз; оформление таблицы отделено от математической модели. У таблицы есть объединённая шапка, заданное выравнивание и один пример OMML в ячейке. Python и reticulate ради этой проверки не добавляются.
3. Сохранить нужные нативные механизмы Word при включении новых таблиц и Book-глав. Сначала проверить готовые API Officeverse и существующий адаптер, затем добавлять минимальное соединение для подтверждённого пробела. Проверить TOC, SEQ/REF и ограниченный пример нативной библиографии; не подменять их похожим статическим текстом.
4. Настроить один реальный набор основного оформления и служебных листов. Затем из тех же глав собрать два состава: курсовую с аннотацией и более короткий состав. Использовать profiles, общие ресурсы и компоненты; общий стиль не копировать в отдельные независимые реализации.
5. Проверить установку и сборку из чистой копии примера с объявленными зависимостями. Добавить короткую инструкцию агенту поверх стандартных соглашений Quarto. Крупную систему команд и универсальных конфигурационных контрактов не разрабатывать без необходимости.

Шаги 1–3 образуют первую техническую сборку. Их результат определяет, оправдана ли связка с flextable в основном пути. Совместимость готовых библиотек проверяется на одном содержательном примере до полировки университетских листов.

## Оставшиеся исследования внутри разработки

| Вопрос | Минимальная проверка | Решение по результату |
|---|---|---|
| Работают ли поля и ссылки нашего адаптера в Book? | Ссылка между двумя главами, TOC после титула, обновление номера после вставки объекта | Переиспользовать рабочее; исправлять только обнаруженную несовместимость. Учесть ограничения штатных ссылок в unnumbered chapters |
| Сохраняется ли редактируемая математика внутри flextable? | OMML внутри w:tc, открытие и изменение формулы через Word с сохранением | Зафиксировать реальную поддержку или ограничение; сначала оценить готовые as_equation/as_qmd, не писать собственный математический конвертер |
| Достаточно ли надёжна Word-финализация? | Обновление, сохранение, закрытие и повторное открытие нового примера | Не скрывать ошибки; отдельно проверить известный сбой Close после PDF-экспорта, прежде чем обещать автоматическую проверку страниц |

Проверка нативной диаграммы mschart — отдельный следующий небольшой пример, если диаграмма входит в ближайшую реальную работу. Наличие chart API уже известно; сквозное включение в Book ещё не подтверждено.

## Исследуемый код и служебное оформление

В базовом сценарии R обслуживает оформление и расчёты, для которых язык не существенен. Если работа посвящена Python, C++, C# или SQL, исследуемый код остаётся на соответствующем языке. Служебное оформление не должно повторно реализовывать этот алгоритм на R.

Листинг можно показывать без исполнения при сборке. Когда нужны результаты запуска, программа может исполняться отдельным воспроизводимым шагом и предоставлять обычные табличные данные, графики и логи. Простой самодостаточный Python-пример допустимо исполнять внутри QMD; требование отдельного процесса для каждого такого примера не вводится.

reticulate остаётся готовым дополнительным инструментом при конкретной необходимости, но смешанное исполнение R/Python не является обязательным интерфейсом агента, условием первого DOCX или отдельной первоочередной задачей. Место исполнения программы не должно размывать её ответственность и источник результатов. Полноценную систему запуска произвольных языков в первую версию не включаем.

## Приёмка первой технической сборки

- Автор редактирует стандартные QMD, метаданные, источники и научный код. Обязательный ручной реестр ресурсов не появляется.
- Одна команда создаёт DOCX и ясно сообщает о сбое. Ручной запуск цепочки отдельных скриптов автором не требуется.
- Изменение одного параметра согласованно обновляет число в тексте, таблицу и график. Форматирование чисел отделено от точности расчёта; универсальное округление без требований не вводится.
- Стили, OMML, таблицы, поля и источники проверены структурно. Новое взаимодействие объектов проверено в настольном Word. Неподтверждённые свойства не выдаются за готовую возможность.
- Результаты оформлены коротко: что штатное, что добавлено нами и почему. Крупные повторные прогоны без новой причины не выполняются.

## После первой сборки

Следующий приоритет — построение нормативной обратной связи агенту с привязкой к исходнику (QMD-файлу, разделу и объекту), зафиксированной в [Политике обратной связи и диагностики](DIAGNOSTICS_POLICY.md).

Непосредственная реализация диагностических проверок начинается после завершения основных программно оформляемых элементов документа (листинги кода, алгоритмы/схемы, приложения, единицы измерения и числовые данные).

Основные направления обратной связи:
1. **Ревизия отказов**: дифференциация критических фатальных ошибок (ошибки схемы Open XML, отсутствие метаданных, невозможность нормативного деления таблицы) и восстановимых замечаний (предупреждения по переносу строк длинных таблиц, вёрстке Word, структуре QMD).
2. **Формат обратной связи**: единая консольная сводка CLI в конце сборки и записи в JSON-отчёте с указанием правила (`SEC_INTRO_MISSING`, `FIG_REF_MISSING`, `TBL_REF_MISSING`), файла QMD, раздела/объекта и понятной рекомендации.
3. **Первые обязательные проверки**:
   - Вводный текст между главой и её первым подразделом (`SEC_INTRO_MISSING`).
   - Вступительный абзац со ссылкой `@fig-id` перед рисунком `#fig-id` (`FIG_REF_MISSING`).
   - Вступительный абзац со ссылкой `@tbl-id` перед таблицей `#tbl-id` (`TBL_REF_MISSING`).
4. **Привязка проблем вёрстки Word**: сопоставление замечаний после сохранения DOCX с ближайшими исходными объектами/заголовками QMD без навязывания слепого `pagebreak`.

Позже, по конкретной работе: техническая рамка и штамп, расширенный набор библиографических типов и требований СТО, редактируемые диаграммы, Excel как источник, экспорт примечаний Word. Эти функции не блокируют первый работающий формат, но их ограничения сохраняются в документации.

AutoNormoKontrol остаётся источником опыта, не зависимостью нового авторского проекта. Нынешний исследовательский стенд сохраняет результаты и проверки; он не переносится целиком в архитектуру продукта.
