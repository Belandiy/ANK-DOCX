# Язык и границы служебного слоя DOCX

Дата: 29 октября 2026 года.

Статус: принято и подключено к рабочей сборке. Собственные Python/PS1-инструменты заменены C#-приложением; исходники сохранены в архиве. Основание — устройство действующего проекта, опыт AutoNormoKontrol, официальные API, interop-проба и последующая [приёмка миграции](research/SERVICE_LAYER_MIGRATION.md). Сравнительное преимущество по времени разработки не измерено.

## Решение

Собственный развивающийся слой обработки DOCX, проверки результата и управления Word строить на **C# и .NET**. Для структуры пакета использовать **Open XML SDK**, для действий над открытым документом — публичный API Word через COM.

Quarto Book сохраняет управление сборкой. knitr, R, flextable, equatags и графические библиотеки сохраняют свои задачи. Lua остаётся штатным способом работы с деревом документа Pandoc там, где это необходимо расширению. Новый универсальный сборщик и собственный парсер QMD не вводятся.

Поддерживаемая служебная инфраструктура больше не содержит собственных Python/PS1. По согласованному пользователем объёму перенесены также установка окружения, проверка Word, экспорт PDF и редактор стилей. Архивы, исследовательские материалы и внутренние файлы сторонних зависимостей этим правилом не удаляются. Не возвращать параллельный Python/PS1-путь для новых продуктовых алгоритмов.

Это решение не обязывает переводить научный код работ на C# и не делает Python недопустимым языком исследуемого проекта.

## Почему решение относится именно к этому проекту

Собственный код уже выходит за рамки запуска команд. Сейчас он создаёт поля и связи Word, преобразует источники библиографии, проверяет структурные условия, согласует страницы и делит длинные таблицы. Планируемая обратная связь также требует доступа к структуре документа и результатам его вёрстки.

На момент выбора в рабочих каталогах было восемь PS1, около 540 непустых строк. Большой PowerShell-движок ещё не сформировался. Алгоритмы разделения таблиц и стабилизации страниц уже требовали устойчивого места; теперь это `WordTables.cs` и `WordFinalizer.cs`.

В проекте есть .NET-валидатор с Open XML SDK 3.3.0. SDK даёт готовую модель пакета и элементов OOXML, а также проверку схемы. Это более предметное основание для C#, чем популярность языка или предположение о меньшем числе строк. SDK не выполняет пагинацию Word и не проверяет смысл научной работы.

Статическая типизация позволяет проверять контракты собственного кода и доступность членов interop-интерфейсов при сборке. Она не устраняет ошибки Word COM во время исполнения, необходимость освобождать объекты и ограничения самого Word.

## Рассмотренные варианты

| Вариант | Польза | Цена и причина выбора/отказа |
|---|---|---|
| Развивать PS1 | Самый короткий переход от текущего состояния; PowerShell доступен в Windows | Сохраняет отдельную модель вывода, коллекций, ошибок и вызова процессов. В AutoNormoKontrol уже обнаружена реальная стоимость сопровождения этих механизмов. Для растущего продукта не выбран. |
| Перевести служебный слой на Python | Удобная автоматизация файлов и процессов, переносимые проверки; доступ к COM через pywin32 | Технически допустим. Для типизированной модели OOXML и текущего SDK-валидатора потребуется выбрать другую библиотеку либо сохранить .NET рядом. В этом проекте основной дополнительный код тесно связан с DOCX/Word, поэтому выбран C#. Это не доказательство, что Python в целом хуже. |
| C# + Open XML SDK + Word COM | Одна экосистема для структурной обработки, валидации и Word-адаптера; проверка типов; возможность выпуска готового приложения | Нужны сборка, организация поставки и interop-зависимости разработчика. COM остаётся сложным. Выбран для собственного служебного слоя с ограниченной областью ответственности. |
| Оставить всё в готовых R-компонентах | Сохраняет один основной вычислительный runtime | Готовые средства использовать везде, где они покрывают задачу. Но `doconv::docx_update()` в нашем конвейере не обеспечил нужный порядок пагинации, а `flextable::paginate()` не создаёт подписи продолжений по фактическим страницам Word. Подтверждённые пробелы остаются нашей ответственностью. Новый прямой COM-слой на R не исследуется без отдельной необходимости. |

Опыт предыдущей миграции не означает автоматического выбора Python. В ADR-0003 AutoNormoKontrol зафиксировано, что Python-пилот оказался длиннее; подтверждённые преимущества относились к переносимости, диагностике и Linux-проверкам. Нельзя обещать снижение стоимости разработки только по синтаксису нового языка.

## Границы ответственности

| Участок | Владелец после перехода |
|---|---|
| Главы, профили, исполнение ячеек, основной вызов Pandoc | Стандартный Quarto Book |
| Расчётные данные, flextable, графики, готовые библиотеки Officeverse | R и библиотеки; код конкретной работы отделён от оформления |
| Разбор QMD и получение дерева документа | Pandoc/Quarto; небольшие штатные Lua-фильтры |
| Применение reference-docx и обычные подписи объектов | Стандартные механизмы Quarto/Pandoc и настройки расширения |
| Недостающие нативные поля и структура DOCX, источники Word, структурные проверки | Собственный модуль C# с готовыми средствами SDK |
| Реальные страницы, обновление полей, разделение таблиц, нормализация Word, экспорт через Word | Ограниченный Windows-модуль C# через Word COM |
| Содержательное название рисунка, корректность выводов, объяснение обозначений | Автор/агент; проверяемые формальные части могут стать отдельными проверками |

Не переносить готовые возможности библиотеки в собственный код ради унификации языка. В частности, не переписывать математический конвертер, flextable, графики или механизм склеивания глав.

Обработку самого DOCX отделить от автоматизации Word зависимостями: модуль пакета и формальных проверок не должен обращаться к COM. Его тесты не требуют Word. Windows-часть может зависеть от этого модуля. Начальная реализация может состоять из небольшой библиотеки и консольного приложения; сервисы, плагины, DI-фреймворк и собственная система заданий не нужны.

Quarto вызывает служебное приложение на завершающем шаге. Команда автора по-прежнему одна. Технические промежуточные данные не становятся новым обязательным авторским форматом.

## Что подтверждено опытом

Ниже описана первоначальная ограниченная проба. Подтверждение последующего полного переноса и рабочей сборки находится в [приёмке миграции](research/SERVICE_LAYER_MIGRATION.md); ограничения самой пробы не подменяют новые свидетельства.

Проба находится в [research/probes/csharp-word](research/probes/csharp-word/README.md). Использованы .NET SDK 10.0.401, runtime 10.0.12, Word 16.0.20326, Open XML SDK 3.3.0 и официальная установленная Word PIA 15.0.4603.1000.

На копии существующего промежуточного DOCX выполнено **одно** разделение таблицы с двухуровневой объединённой шапкой. Проверены вызов `Selection.SplitTable`, копирование `FormattedText`, сохранение строк и итога, объединений и повторяемой шапки, редактируемой математики OMML, нативного REF, корректного NUMPAGES, сохранение/повторное открытие, схема SDK и завершение собственного процесса Word.

Итог: сборка без предупреждений и ошибок; 11 проверок успешны, 0 ошибок схемы SDK, exit code 0. Interop-типы встроены в приложение, отдельной зависимости от Word PIA в списке ссылок результирующей сборки нет.

Первая попытка не прошла проверку NUMPAGES. После сохранения проверенного порядка нормализации из текущего PS1 — сохранение, повторное открытие и стабилизация числа страниц — итоговая проба прошла. Отрицательный результат сохранён. Смена языка не заменяет этот алгоритм.

Проба **не подтверждает** полный перенос финализатора, разделение всех фрагментов таблицы, всю матрицу неподдерживаемых входов, качество PDF, совпадение всей вёрстки, поставку на чистой машине или сборку в Linux. Она подтверждает отсутствие выявленного блокера для конкретных interop-операций в выбранном .NET.

## Зависимости и ограничения поставки

1. Не использовать неподдерживаемую NuGet-перепаковку `Microsoft.Office.Interop.Word` 15.0.4797.1004 как будто это официальный поддерживаемый пакет Microsoft. На её странице указан сторонний владелец и неподдерживаемый статус. В пробе использована PIA установленного Office с `EmbedInteropTypes=true`.
2. Для сборки Windows-адаптера разработчику нужна официальная PIA из поддерживаемой установки Office/средств разработки. Путь задаётся явно; путь GAC этой машины не становится обязательным путём проекта. Автоматическая установка средств разработки и юридические условия конкретного способа распространения должны быть проверены при подготовке поставки.
3. Используется self-contained-публикация. Опубликованное приложение проверено с пустым PATH и несуществующим DOTNET_ROOT; ему не нужен отдельно установленный .NET runtime. Установка на совершенно чистой машине пока не испытана. Настольный Word остаётся зависимостью, для сборки исходников нужны SDK и официальная PIA.
4. Структурную обработку DOCX можно отделить от Windows. Готовый выпуск сейчас по-прежнему требует настольного Word. Кроссплатформенный выпуск всего документа и серверная автоматизация Office этим решением не обещаются.
5. Ошибки промежуточного OOXML до Word, известный сбой закрытия после PDF-экспорта и ограничения длинных таблиц остаются открытыми ровно в прежнем объёме. Язык не является их исправлением.

## Порядок перехода

Согласованный переход Python/PS1 завершён: пункты 1–3 и инструменты из пункта 6 выполнены. Ниже сохранены границы миграции. Прямые преобразования пакета в R-hook пока сохранены; пункт 4 — отдельный следующий участок, а не скрытая параллельная реализация Word-адаптера. Пункт 5 выполняется по новым требованиям.

1. Первым переносимым продуктовым участком сделать **Word-финализацию**: `update-word.ps1` и `tables-word.ps1`. Сохранить рабочий Quarto-вызов, публичный API Word, порядок пагинации и ограничения входов. Проба не становится автоматически кодом продукта.
2. До переключения сравнить результаты с действующим конвейером на существующих случаях: обычный документ, длинная таблица с объединениями и OMML, два и несколько фрагментов, ссылки и NUMPAGES. Проверить ошибки неподдерживаемых таблиц, сохранение данных и завершение только своего Word. Проверки должны учитывать состав нового документа, а не только жёстко заданные числа старого примера.
3. После подтверждённого переключения удалить заменённую PS1-реализацию. Не сохранять постоянный fallback и две реализации одного алгоритма. Сбой новой финализации должен оставаться сбоем.
4. Затем переносить прямую структурную обработку из `finalize.R` в модуль SDK по завершённым операциям. В R оставить настройку библиотек и вызов завершающего приложения. Схемную проверку выполнять до и после Word; не приписывать текущие ошибки одному upstream-компоненту без доказательств.
5. Новые формальные проверки и извлечение примечаний добавлять в этот же служебный слой по реальным требованиям. Возможности, относящиеся к дереву исходников, оставлять в стандартном механизме Pandoc, с минимальной передачей необходимых сведений.
6. Сценарии установки и вспомогательный редактор стилей переносить при конкретной выгоде. Они не блокируют остановку роста продуктовых алгоритмов на PowerShell.

Для каждого нового изменения оценивать готовое средство, границу собственного кода, зависимости и проверку поведения. Число файлов и строк не служит самостоятельным критерием успеха. Не начинать новый общий рейтинг языков при каждой функции; вернуться к решению при изменении платформы, отсутствии нужного API или измеренном росте стоимости сопровождения.
