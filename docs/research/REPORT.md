# Сравнение officedown и Python с Pandoc

Дополнение: практический опыт Quarto, двух составов работы и вычислений описан отдельно в [QUARTO_REPORT.md](QUARTO_REPORT.md). Ниже сохранено исходное сравнение A/B; вариант B не использует Quarto.

Исследовательский эксперимент выполнен 28 октября 2026 года на Windows с настольным Microsoft Word. Оба прототипа создают редактируемую демонстрационную работу из одинаковых исходных файлов и запускаются одной командой. Полноценный новый DOCX writer для этого не потребовался. При этом officedown не заменил собственную логику библиографии, метаданных, приложений и финальной проверки.

Итоговые документы: `output/a-officedown.docx` и `output/b-python-pandoc.docx`. Каждый содержит 10 страниц, два рисунка, три таблицы, шесть нумерованных формул, две inline-формулы, два приложения и три библиографических источника. Это небольшой технический корпус, не полноценная курсовая с исследовательскими результатами и не проверка соответствия ГОСТ.

## Устройство сравнения

Общие входы: `demo/project.yaml`, два Markdown-файла в `demo/content/`, `demo/sources.json`, PNG и текстовое описание схем в `demo/assets/`. Входы и их SHA-256 перечислены в `build/comparison-evidence.json`.

**A:** Python-оболочка автоматически переводит семантическую нотацию в Rmd; R Markdown/officedown/officer создают подписи, закладки и поля. Математику записывает Pandoc. Автору не нужно писать R chunks.

**B:** та же оболочка передаёт Markdown Pandoc; собственный Lua-фильтр создаёт SEQ, REF, TOC и закладки. Математику также записывает Pandoc.

У обоих вариантов одинаковый reference.docx и общий небольшой слой Python/OOXML для реквизитов, библиографии Word, приложений, размещения номеров формул и таблиц. Word завершает сборку: обновляет stories и TOC, выполняет пагинацию, сохраняет результат. Таким образом, A здесь тоже использует Python для оболочки и общего слоя. Это выбор устройства сравнительного стенда, а не доказательство, что аналогичный слой нельзя написать на R.

Для каждого варианта сохранены три состояния: `*-raw.docx`, `*-native.docx` и итог после Word. В raw A уже используется адаптер и явные вызовы officer для формул; raw B уже содержит собственный Lua. Дополнительный `build/pandoc-stock.docx` показывает вывод Pandoc без этих механизмов. Термин raw не означает нулевой объём собственного кода.

## Что дали готовые механизмы

officedown подтвердил полезность своих подписей и ссылок. Для изображений достаточно автоматически создать chunk с `knitr::include_graphics` и подписью. Для таблиц первая попытка оставить обычные Markdown captions не создала SEQ; адаптер перевёл те же ячейки в data.frame с `tab.id`/`tab.cap`, после чего заработал штатный принтер officedown. Это пример реальной стоимости адаптации общего Markdown-входа.

Нумерацию формул A получил через явные вызовы `officer::run_autonum`, TOC — через `officer::block_toc`. Самостоятельно писать XML этих полей в A не понадобилось. В B аналогичные инструкции и закладки формирует 49 строк Lua. Оба пути используют один Pandoc 3.10, поэтому одинаковое качество математического преобразования не является независимым преимуществом R или Python.

Обычный citeproc у обоих формировал текст библиографии и ссылки-гиперссылки. В raw-файлах отсутствуют CITATION, BIBLIOGRAPHY и встроенные источники. Их создаёт **общий собственный слой**, а не officedown. Встроенная библиография проверена отдельно от Zotero: Zotero в этом эксперименте не устанавливался и не использовался.

## Библиография и обновление

Первый вариант XML источников использовал namespace из старого примера Word API: `http://schemas.microsoft.com/office/word/2004/10/bibliography`. Файлы имели поля CITATION, но Word видел ноль источников и показывал недопустимый источник. При упаковке в DOCX сработал `http://schemas.openxmlformats.org/officeDocument/2006/bibliography`, корректные OPC-связи и properties части custom XML. Свидетельства неудачи сохранены в `build/*-bibliography-failed-first.json`.

Документация [Word API](https://learn.microsoft.com/en-us/office/vba/word/concepts/working-with-word/working-with-bibliographies) описывает добавление Source XML, а [модель Sources Open XML SDK](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.bibliography.sources?view=openxml-3.0.1) относится к представлению пакета. Пример входа API нельзя без проверки считать готовой структурой библиографической части DOCX.

Три короткие пробы редактирования уже загруженного источника дали ограничения: `LoadXML` нельзя повторно применять к загруженной части; изменение CustomXMLNode.Text было затёрто кэшем библиографии Word; удалить процитированный источник через Source.Delete нельзя, а Add с существующим тегом завершился ошибкой. Для доказательства обновления использована явная правка закрытого пакета и повторное открытие. Универсальный адаптер редактирования источников в работающем Word не реализован.

`w:updateFields` помог Word начать пересчёт некоторых объектов при открытии, но в первом снимке NUMPAGES ещё показывал 1. Только явные обновления stories/TOC и Repaginate дали согласованное число страниц. Поэтому в стенде есть обязательная финализация, а «откроется и само всё обновит» не является контрактом.

## Корректность пакета и вёрстка

Пакеты дополнительно проверены Open XML SDK 3.3.0 для Microsoft365. Результаты последнего структурного сравнения:

| Состояние | A | B |
|---|---:|---:|
| Вывод backend с адаптером | 65 замечаний схемы | 4 замечания схемы |
| После общего слоя, до Word | 59 | 4 |
| Итог после обычного открытия и сохранения Word | **0** | **0** |

В A обнаружены, в частности, GUID вместо числового ID закладки, dirty на instrText и отсутствие tblGrid; в математике Pandoc — порядок элементов свойств матрицы. Общий слой исправляет сетку и формат таблиц, но не является полноценным нормализатором OOXML. Word нормализует оставшуюся разметку при обычном сохранении. OpenAndRepair не вызывался. Эти числа относятся к конкретным версиям и корпусу, не ко всем документам библиотек.

Свидетельства: `build/sdk-validation.json`, `build/final-sdk-validation.json`. Оба финальных пакета не имеют замечаний SDK; это не означает полного нормативного соответствия или поддержки любых изменений.

Одинаковый reference.docx не дал полностью одинаковую вёрстку: отличаются выделение префиксов подписей, отступы ячеек, выравнивание числовой колонки и некоторые переносы. В частности, заключение начинается на странице 6 у A и на странице 7 у B. Эти различия видимы в выходных файлах и должны учитываться при последующей настройке оформления; полное визуальное равенство не объявляется.

Визуальная проверка использовала PDF, экспортированные самим Word, и PNG каждой страницы. Штатный render_docx.py не запустился из-за отсутствия LibreOffice; альтернативный движок вёрстки не подменял поведение Word. Проверены все страницы двух финальных файлов: формулы читаемы, изображения встроены, таблицы не имеют узких столбцов с посимвольным переносом, поля не показывают ошибок. Исправление ширин и абзацных отступов таблиц потребовалось особенно B; общая логика применена к обоим вариантам. Полировка под конкретный вуз не выполнялась.

Версии перечислены в `dependencies.lock.json`. .NET/SDK-валидатор — проверочный инструмент, не обязательная зависимость выдачи.

## Ограничения математики

На положительном корпусе оба пути записали восемь OMML-зон: четыре дроби, два матричных контейнера, один eqArr и другие структурные элементы. Word сохранил изменение числителя, что подтверждает редактируемость проверенной структуры.

Отрицательные пробы Pandoc и повторный прогон через officedown показали:

| Выражение | Наблюдение |
|---|---|
| Неизвестная команда | Предупреждение и буквальный TeX, без OMML; механизм не работает для этого ввода |
| TikZ внутри math | Предупреждение и буквальный TeX; это не поддержка диаграмм |
| Простой newcommand с одним аргументом | Развёрнут в нативное выражение x²; нельзя объявлять все макросы неподдерживаемыми |
| tag вместе с label | В данном примере предупреждение и буквальный TeX; номер и связь следует задавать семантически отдельно |

Во всех этих пробах Pandoc мог вернуть exit code 0. Поэтому успех процесса не равен успеху преобразования математики. Обычная команда сборки теперь отклоняет обнаруженное предупреждение о таком fallback. Автоматическое покрытие произвольных LaTeX-пакетов не заявлено.

## Решение по дальнейшему развитию

Высокоприоритетные результаты итоговых файлов близки: оба пути дают нативные основные объекты и проходят одинаковый стресс-сценарий. Для автора интерфейс одинаков: несколько текстовых файлов и одна команда. У officedown есть готовая логика полей и удобный путь для R-таблиц; B требует своего небольшого Lua, но обходится без R. Количество зависимостей само по себе не перевешивает качество результата.

Эксперимент поддерживает идею **небольшой академической надстройки над существующим writer**. В её необходимый объём сейчас входят: семантические ID и проверки входов, шаблон и метаданные, выбранный механизм библиографии, правила приложений и статистики, финализация и контроль результата. Реализовывать собственный полный DOCX writer оснований нет.

Окончательного победителя назначать рано. Для текстовых работ текущий B выглядит компактным кандидатом по составу окружения; для работ с существенной R-аналитикой A может оказаться удобнее. Для выбора следующего шага важнее проверить два оставшихся практических разрыва: обычную вставку подписи через интерфейс Word с тем же счётчиком и обновление статистики после ручных правок. Отдельное решение нужно о том, приемлема ли обязательная установленная копия Word. Если нет, следует исследовать нормализацию и заполнение полей без Office, начиная с обнаруженных замечаний SDK.

Открыты также: редактирование библиографии через диалог Word, книги/статьи/DOI, нужный нормативный стиль, перестановка и копирование объектов, длинные формулы и таблицы, другая версия/локаль Word, Linux и чистый компьютер получателя. Эти вопросы не засчитаны выполненными.
