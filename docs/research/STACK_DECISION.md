# Выбор основы по расширенным требованиям продукта

Обновление 29 октября 2026 года: создано первое расширение и стандартный Book-пример Quarto + R + flextable. Сложная таблица, OMML в ячейках и согласованный пересчёт подтверждены; результаты и ограничения — в [EXTENSION_REPORT.md](EXTENSION_REPORT.md). Нативные диаграммы и reticulate ещё не испытаны. Ниже сохранена оценка предыдущего этапа, а новые данные об агентных сценариях находятся в [QUARTO_ECOSYSTEM_AUDIT.md](QUARTO_ECOSYSTEM_AUDIT.md).

Текущее рабочее направление — Quarto и стандартный QMD как среда авторских исходников и упаковки университетского формата; базовый вычислительный путь первой версии — knitr и R с готовыми средствами Officeverse. Когда язык не существенен для темы, расчёты также можно выполнять на R. Исследуемый Python/C++/C#/SQL-проект сохраняет свой язык; оформление не должно дублировать его алгоритм. Предметное преимущество готовых Word-компонентов относится к officer, flextable и mschart; оно не требует автоматически выбирать R Markdown как единственную авторскую платформу. R Markdown с officedown остаётся проверенной альтернативой. Прямой Python с Pandoc сохраняется как контрольная реализация.

Принцип дальнейшей работы закреплён в AGENTS.md: сначала проверить готовые средства и уже полученные результаты, затем испытать конкретную недостающую интеграцию, собственный код писать для подтверждённого пробела. Возможность получать нативный DOCX через дополненный Quarto заново доказывать не требуется.

Это оценка покрытия требований и доступных API, не новый результат сравнительного стресс-теста. На следующем этапе сложная таблица уже испытана в расширении. Нативные диаграммы остаются непроверенными: наличие body_add_chart у mschart не означает, что любой объект диаграммы автоматически печатается через knitr в нужное место работы без обвязки.

Причина прежней неопределённости: стенд доказал возможность получить сходные основные объекты, используя общий Pandoc и собственное завершение. Он не сравнил всю экосистему Office-компонентов и не измерил работу независимых агентов. Выбирать основу продукта только по тем двум DOCX или строкам фильтра было недостаточно.

## Python при использовании knitr и flextable

Приоритет уточнён пользователем: это дополнительная возможность для пограничного сценария, а не основной путь продукта. Первая сборка проверяет R + flextable напрямую. Служебное оформление, расчёты работы и исследуемый программный проект разделяются по ответственности; расположение кода внутри или вне QMD само по себе эту границу не определяет.

Уточнение 29 октября 2026 года: выбор knitr не требует выполнять научные расчёты на R. Официальная документация Quarto описывает исполнение Python-ячеек через reticulate при использовании knitr. reticulate предоставляет доступ к Python-объектам из R через py и преобразования распространённых типов, включая pandas DataFrame и NumPy-массивы.

Это позволяет сохранить алгоритм, графики и выводимые листинги на Python, а R использовать только для оформления таблицы flextable из рассчитанных данных. Код оформления можно скрыть в итоговой работе. Не следует создавать две независимые реализации одного научного расчёта на разных языках.

Цена этого варианта — два языка в среде сборки, настройка конкретного Python-окружения и границы преобразования типов. Произвольные Python-объекты не следует считать автоматически пригодными для flextable. Полный гибридный конвейер с Word-проверкой здесь ещё не запускался; это документированная готовая интеграция, а не новый результат стенда.

Для новой работы можно выбрать Jupyter/Python с тем же университетским оформлением, если расширение не привязано к R-вычислениям и R-объектам. Однако существующие R-ячейки, inline R и вызовы flextable не переводятся в Python сменой параметра engine. Текст, стандартная разметка, математическая запись, библиографические данные и Word-стили обычно переиспользуются; исполняемый и зависящий от библиотек код требует адаптации.

Пока в выбранном конвейере используется flextable, R остаётся зависимостью. Избавление от R требует замены генерации этих таблиц или отдельного заранее подготовленного представления, а не только выбора другого движка. Нативные поля Word и конечная проверка документа остаются отдельной частью сборки при любом вычислительном движке.

Источники: [Quarto: engine binding и совместное использование Python/R](https://quarto.org/docs/computations/execution-options.html#engine-binding), [reticulate: Python-ячейки и обмен объектами](https://rstudio.github.io/reticulate/articles/r_markdown.html), [flextable: включение таблиц через knitr](https://davidgohel.github.io/flextable/reference/knit_print.flextable.html).

## Сложные таблицы и диаграммы

У flextable есть публичные функции объединения произвольного прямоугольного диапазона и управления горизонтальным и вертикальным выравниванием. Автор описывает структуру таблицы через известный API. Отдельный JSON-реестр каждой таблицы не обязателен. Шрифты и общее оформление можно задать один раз. Это не означает, что движок может сам угадать содержательное объединение ячеек.

Quarto тоже не ограничен pipe tables: поддерживает list tables и HTML со colspan/rowspan, которые преобразуются для других форматов. В текущей документации DOCX поддерживает text-align из HTML, а vertical-align этим путём не поддерживается. Чистый Markdown имеет предел выразительности; сложной таблице потребуется стандартная структурная разметка либо код табличной библиотеки. Интеграция этих вариантов с нашим фильтром C ещё не проверена.

Уточнение: сам Pandoc Markdown тоже поддерживает объединения в grid tables. Это общая возможность для всех путей через Pandoc; для одного объединения ячеек flextable не требуется. Минимальный опыт `scripts/probe-table-mechanisms.py` с установленным Pandoc 3.10 подтвердил в DOCX `w:gridSpan=2` и пару `w:vMerge restart/continue` из Markdown без Lua и OOXML-обработки. Проверена структура пакета, не новый сценарий настольного Word. Преимущество flextable относится к удобству детального управления оформлением и генерации таблиц из данных, а не к исключительной способности создавать объединённые ячейки.

mschart записывает диаграмму Office вместе с данными в документ; результат предназначен для дальнейшего редактирования. Поддерживается определённый набор видов диаграмм, а не произвольный график ggplot2. Это отличается от PNG/SVG графика. Блок-схемы, UML и SmartArt — ещё другая задача; готовую поддержку их редактирования как фигур Word мы не подтверждали.

Локально проверен API установленного python-docx 1.2.0: add_comment и объединение ячеек есть, add_chart на Document нет. Это ограничение этой библиотеки, не доказательство отсутствия всех сторонних Python-решений. Подключение ещё одного writer или собственная генерация chart OOXML изменили бы стоимость и устройство варианта Python.

## Формулы с переменными

Нужно разделять три результата: символическое выражение, подстановку параметров и рассчитанное значение. Оба вычислительных пути могут подготовить LaTeX из результатов и передать его Pandoc. Для обычной подстановки достаточно стандартных inline-выражений или вывода Markdown из ячейки. Для одного символического определения, из которого выводятся формула и численный расчёт, полезна символьная библиотека, например SymPy в Python; это дополнительная научная возможность, а не свойство DOCX.

Изменили параметры и пересобрали — выражение, числа и графики могут согласованно измениться. Изменили число непосредственно внутри готового Word — R/Python автоматически не запускаются. Второе поведение потребовало бы отдельного вычислительного механизма или интеграции, независимо от officedown/Quarto. Редактируемость OMML и вычислимость формулы — разные свойства.

Отдельная возможность — вычисляемые поля в ячейках Word, например `=SUM(ABOVE)`, `=PRODUCT(LEFT)` или ссылки A1/RnCn. Это иной механизм, чем OMML. Можно принять знакомую запись формулы в ячейке Markdown и преобразовать её в поле Word небольшим фильтром. В stock Pandoc 3.10 из опыта выше `=SUM(ABOVE)` остаётся обычным текстом, полей не появляется. Автоматическое преобразование ещё не реализовано; в officer уже есть общий API run_word_field для записи поля.

Уточнение после изучения Officeverse целиком: для стандартного R-пути существует и `flextable::as_word_field()` — готовый API вставки поля Word в ячейку. Поэтому собственный перевод обычного текста Markdown в поле нужен только при выборе такого авторского соглашения; R-автор может пользоваться библиотечным API. Обновление значений всё равно выполняет Word. Полный опыт с SUM в нашем конвейере пока не проведён.

По документации Microsoft формулы таблиц вычисляются при вставке/открытии; после изменения значений их можно обновить F9. Это ограниченный язык Word, не полная совместимость с Excel. Для локальных итогов и произведений такая функция полезна. Основные расчёты исследования, от которых зависят также графики и проза, разумно сохранять в одном вычислительном источнике: пересчёт поля Word не пересчитает Python/R и их изображения. Сложные ссылки, объединённые ячейки, порядок обновления зависимых полей и русское числовое оформление ещё требуют целевого опыта.

Пользователь уточнил, что пересчёт уже выданного Word необязателен. Для обычных табличных итогов тоже можно использовать R: данные и результаты вычисляются один раз, затем выводятся в прозе, Markdown-таблице или flextable. Стандартный R Markdown уже даёт inline R и скрытые блоки кода, отдельный язык вычислений не требуется. R является самостоятельным языком вычислений и графики; интеграцию с Markdown обеспечивают knitr/R Markdown.

## Обратная связь по сборке

Сообщения «таблица 8 на странице 16 занимает слишком много места» или «на странице 7 почти нет основного содержимого» относятся к анализу уже свёрстанного документа. Предлагаемая последовательность:

1. Проверить исходники и ссылки до сборки.
2. Создать DOCX, обновить поля и получить окончательную вёрстку.
3. Связать объект с текущим номером страницы и исходным файлом через устойчивый ID/закладку.
4. Проанализировать геометрию, структуру и изображения страницы.
5. Выдать человеку и агенту сообщение с объектом, источником, измерением и предлагаемым действием.

Например: «Таблица tbl-results, текущий номер 8, страница 16, content/results.Rmd:72. Таблица занимает 86% полезной высоты страницы. Рассмотрите разделение или перенос в приложение». Формат отчёта генерируется программой; агенту не нужно заполнять его вручную.

Порог заполненности нужно применять к полезной области страницы, с исключениями для титула, задания, аннотации, концов разделов и намеренных разрывов. Доля белых пикселей сама по себе не является корректной мерой: у обычной текстовой страницы много белого пространства. Замечание «над рисунком нет текста» требует учитывать продолжение с предыдущей страницы и правила конкретного СТО. Такие находки следует отделять от достоверных структурных ошибок. Нельзя автоматически дописывать содержательный текст ради заполнения страницы.

Word API предоставляет номера страниц диапазонов. У координат Range.Information есть ограничения видимости: для элементов вне видимой области могут возвращаться -1. Поэтому полную геометрию нельзя обещать получить одним вызовом в скрытом Word. Возможный практический путь — Word для нумерации/закладок и его PDF для геометрии. Это ещё не реализованный полноценный анализатор.

В AutoNormoKontrol уже есть проверка заполнения по координатам текста PDF: postflight.py оценивает занятую высоту рабочей области и выдаёт findings. Это полезный опыт, но механизм не учитывает всю геометрию Word-объектов и не переносится в DOCX как готовая функция.

## Комментарии как задания агенту

Для чтения сохранённых базовых примечаний отдельная надстройка Word не обязательна: officer и python-docx предоставляют доступ к комментариям. Нужен экспорт текста замечания, цитируемого фрагмента и связи с исходным объектом. Можно сформировать файл задания или текст, который пользователь передаст агенту. Это не требует синхронизации всех правок Word обратно в Markdown.

Надстройка оправдана для работы в открытом Word: выбрать замечания, нажать кнопку экспорта, увидеть результат. Это независимый от основного writer интерфейс. Современные ветки обсуждений, mentions и resolved-состояния требуют проверки отдельных API и версий; поддержку всех вариантов комментариев стенд не доказал.

## Excel и вычисления

Получать исходные данные из XLS/XLSX можно и на R, и на Python без установленного Excel. Но чтение значений ячеек не гарантирует пересчёт книги. Например, openpyxl прямо указывает, что не исполняет формулы. Для Excel как вычислительного движка нужно отдельно выбрать способ пересчёта и проверить актуальность результатов. Изменение исходной книги не создаёт автоматически живую ссылку из уже выданного DOCX: базовый сценарий — пересборка работы.

## Страницы без Word и масштабирование

Если под «работать без docx» имеется в виду отсутствие установленного Microsoft Word, оба пути умеют создавать пакет DOCX без него. Получение точной вёрстки Word и обновление всех механизмов — отдельная задача. LibreOffice может быть альтернативным движком для предварительной проверки, но совпадение страниц с Word требует проверки, особенно для сложных объектов.

Для серверного масштаба существеннее зависимость от настольного Word, чем выбор R/Python. Microsoft не рекомендует и не поддерживает обычную unattended server-side Automation Office. Разумно отделить независимую генерацию и проверку исходников от завершающего клиентского шага Word. Сравнительной статистики скорости в одинаковом расширенном сценарии у нас пока нет.

В FAQ Officeverse для готового обновления полей рекомендуется `doconv::docx_update()`. Его документация указывает использование установленного Microsoft Word: PowerShell/COM на Windows и AppleScript на macOS. Функция не вычисляет поля самостоятельно без Word. Это кандидат на замену части собственной финализирующей обвязки, но не проверенный в стенде обход найденного сбоя PDF-экспорта. Новые пакеты в этом уточнении не устанавливались и интеграционный тест doconv не запускался.

При жёстком требовании Office-free пагинации можно отдельно оценивать полноценный layout engine. Например, коммерческий Aspose.Words предоставляет LayoutCollector с привязкой узлов к страницам. Это не испытанный нами вариант и не гарантия совпадения его вёрстки с Word. Нельзя приписывать эти функции автоматически другим редакциям продукта, включая FOSS.

Если имелся в виду выпуск ещё и PDF/HTML из одних исходников, Quarto имеет сильное готовое окружение для такой публикации; R Markdown тоже многоформатен. Но специфичные нативные объекты Word в обоих случаях потребуют представлений для других форматов. Это отдельный критерий от отсутствия Microsoft Office.

«Несколько форматов публикации» означает разные выходы DOCX/PDF/HTML, а не смену стиля или вида работы. Смена Word-шаблона и сохранение общей обезличенной содержательной части доступны и в officedown; исключительного преимущества Quarto здесь нет.

## Шаблоны и рамки

Вместо отдельного полного шаблона каждой работы целесообразны два независимых выбора: семейство оформления основной части и состав документа. Например, гуманитарное/техническое оформление плюс курсовая/реферат. Агент выбирает готовые варианты, а не описывает рамку заново.

Рамка, технический штамп, колонтитулы, поля и начало нумерации относятся также к секциям, а не только к именованным стилям. Импорт DOCX-фрагментов должен согласовывать стили и нумерацию: officer::body_import_docx переносит нумерации, но не копирует стили автоматически и предоставляет mapping. Возможность импортировать документ не равна гарантии сохранения произвольного технического бланка.

Важное уточнение исследования: установленный Pandoc 3.10 действительно возвращает OOXML-шаблон по команде `pandoc --print-default-template=docx`. Современная документация описывает `default.openxml` для метаданных, служебного текста и положения TOC. Поэтому нельзя считать Python-обработку этих частей обязательной. Тело reference.docx по-прежнему не служит шаблоном содержимого, но reference.docx и отдельный Pandoc template — разные механизмы. Здесь проверено наличие шаблона, не полный перенос нашей компоновки на него.

## Происхождение обозначений

- `{#identifier}` — синтаксис атрибутов Pandoc Markdown.
- `#sec-method`, `#eq-energy`, `#tbl-results` и ссылки `@sec-method` — документированные соглашения Quarto.
- `fig:`, `tbl:`, `eq:`, `sec:` и ссылки вида `[@fig:...]` используются в pandoc-crossref; подобная нотация уже была в AutoNormoKontrol. Она не является командой встроенного DOCX writer Pandoc.
- officedown использует синтаксис bookdown, например `\@ref(fig:plot)` и `\@ref(tab:results)`.
- Конкретная поддержка этих обозначений, `.equation` и служебных маркеров `[[TOC]]`, `[[STATS]]` в нашем стенде — проектная реализация. Она не доказывает, что Pandoc сам превращает любую такую метку в SEQ/REF.

Для продукта стоит выбрать один документированный авторский синтаксис выбранной экосистемы. Перевод между несколькими нотациями нужен был сравнительному стенду, но не обязан оставаться пользовательским интерфейсом. Метаданные работы и библиографические записи нужны; отдельный вручную заполняемый реестр ресурсов не должен быть обязательным, если ID, подпись и путь уже находятся в исходнике.

## Практический выбор

При приоритете именно богатого редактируемого Word-документа готовые Office-компоненты дают семейству officedown более предметное преимущество. Цена — R как основной вычислительный путь, его пакеты, Word-специфичные части исходников и неизбежные границы поддерживаемых объектов. Нативная библиография по СТО и анализ вёрстки всё равно остаются собственной работой.

Quarto с Python предпочтительнее, если главным становится Python-исследование и публикация в нескольких форматах, а дополнительный документный слой приемлем. У него нет доказанного преимущества по сохранности нативных Word-полей; наш вариант C достиг этого с дополнительными фильтрами. Добавлять одновременно обе авторские платформы в основной путь сейчас не требуется.

Минимальные оставшиеся проверки для обоснования продуктового выбора: сложная таблица с многоуровневой шапкой и разным выравниванием; нативная диаграмма с редактируемыми данными в полном Rmd-конвейере; реальный технический бланк; извлечение примечания и одна диагностика геометрии со связью с исходником. Эти проверки адресуют конкретные риски, а не повторяют первоначальную курсовую целиком. Большой сравнительный тест агентов для этого не обязателен.

Officeverse разумно рассматривать как готовую техническую основу, но процент покрытия всего академического продукта пока не измерен. Стили и обратная связь — важные части нашей надстройки, однако остаются композиция служебных листов и метаданных, выпуск одной командой с понятными ошибками, а при сохранении требования нативной библиографии — интеграция источников Word и проверка требований вуза. Слой перевода единой нотации MD между A/B/C служил сравнению; стандартный Rmd в основном продукте может сделать его ненужным. Это не требует писать новый DOCX writer.

## Уточнение Quarto с R и математические модели

Выбор авторской платформы и вычислительного языка независим. Quarto может исполнять R через knitr; его применение не обязывает выбирать Python. Поэтому важная ограниченная альтернатива R Markdown/officedown — Quarto с R и компонентами Officeverse. Связка Quarto + R + flextable-qmd ещё не испытывалась в нашем стенде. Смена расширения Rmd на qmd не переносит автоматически R Markdown output format и обработчики officedown.

Официальный FAQ Quarto описывает активное развитие новых возможностей Quarto, но прямо сохраняет поддержку R Markdown и отсутствие планов его deprecation. Поэтому «новее» не является самостоятельным основанием менять работающий Word backend. Наш дополненный Quarto/Python уже прошёл тесты SEQ/REF и встроенной библиографии; утверждение, что все Word-поля Quarto-прототипа ещё не проверены, устарело. Эти поля создаёт наш слой, а не stock Quarto.

Текущая документация flextable подтверждает as_qmd и расширение flextable-qmd. Это встроенное Markdown-содержимое одного абзаца ячейки; блочные списки, заголовки, кодовые блоки и несколько абзацев таким способом не вставляются. Для маркированных DOCX-таблиц документирован дополнительный post-render фильтр unwrap-float.lua. Сама возможность inline code не является доказательством позднего исполнения произвольного R/Python внутри строки: расчёты и обработка Markdown относятся к разным этапам. NEWS flextable относит появление as_qmd к 0.9.11; эта версия функции не проверялась локальным запуском.

as_equation использует equatags, а проект equatags прямо заявляет генерацию Office Open XML Math. Поэтому готовый путь к нативной математике внутри flextable имеет документальное основание; считать его заведомо картинкой нельзя. Нужны проверка фактического OOXML и редактирование выражения в ячейке через Word, особенно при объединении ячеек, переносах и совместной работе фильтров Quarto.

Единая символьная модель — отдельное требование от простого пересчёта чисел. SymPy документирует и подстановки subs, и генерацию LaTeX из одного выражения. Это реальное преимущество готовой символьной библиотеки, а не самого Quarto. При этом цепочка «f(2)=3·2²+1=13» требует управления представлением промежуточной подстановки: обычная подстановка может сразу упростить выражение до 13. Автоматическая генерация всего учебного вывода одним вызовом не доказана.

Предложенный пример пригоден для узкого опыта: f(x)=a*x^2+b, g(x)=2*x, x=[2,3,4], b=1. При a=3 итог f+g равен 108, при a=5 — 166. В таблице должны меняться число, отображаемые коэффициенты/подстановки и график. Для реального варианта строки следует получать из набора данных, а не фиксировать f[1]/f[2]/f[3] в Markdown: добавление точки x тоже должно отражаться без ручного дописывания строк.

Не требуется заново испытывать четыре полных конвейера. Новую неопределённость адресует одинаковый расчёт на R в Rmd/officedown и Quarto/R/flextable, с проверкой OMML в ячейках и сохранения нативных подписей/REF. Символьную модель можно проверить отдельным коротким опытом SymPy, не делая Python и второй интерпретатор обязательными для всех работ. Все эти дополнительные опыты остаются предложением, а не выполненными тестами.
